# 模块 0：Cloud Runtime 全局概览与设计哲学

## 一、什么是 Cloud Runtime？

Cloud Runtime（云运行时）是一个**在云端执行用户代码的执行环境抽象层**。

这句话拆开来看有三个关键词：

- **云端**：意味着资源是共享的、弹性的、按需分配的
- **执行环境**：意味着需要隔离、需要资源限制、需要生命周期管理
- **抽象层**：意味着用户不需要关心底层细节，只需要声明"我要什么"

### 从历史演进理解

理解一个系统的最好方式是理解它**为什么诞生**。Cloud Runtime 不是某个人某天设计出来的，而是沿着一条清晰的演进路径发展而来的：

```
物理机 → 虚拟机 → 容器 → Serverless/FaaS → Cloud Runtime
```

每一层演进都解决了前一层的核心矛盾：

| 阶段 | 解决了什么问题 | 遗留了什么新问题 |
|------|---------------|-----------------|
| 物理机 | — | 资源利用率低，部署慢，隔离差 |
| 虚拟机 | 隔离性、硬件利用率 | 启动慢（分钟级），资源开销大（每个 VM 需要完整 OS） |
| 容器 | 启动快（秒级），轻量（共享内核） | 隔离性弱（共享内核），安全攻击面大 |
| Serverless | 无需管理基础设施，按需付费 | 冷启动延迟，执行时间限制，调试困难 |
| Cloud Runtime | 综合解决以上所有问题 | 系统复杂度极高 |

**Cloud Runtime 的本质**：在保持容器级轻量的同时，提供虚拟机级隔离，并具备 Serverless 的弹性伸缩能力。这是一个**不可能三角**的工程权衡：

```
        隔离性（安全）
           /\
          /  \
         /    \
        /      \
       /________\
  轻量性 ←→ 弹性
```

不同的工业方案在这个三角中选择了不同的位置：

- **Firecracker**（AWS Lambda 底层）：偏隔离性 — 用 Rust 写的 microVM，启动时间 125ms，但每个 VM 有独立内核
- **gVisor**（Google）：偏隔离性 — 用户态内核，拦截系统调用，但性能损耗 10-30%
- **Kata Containers**：偏隔离性 — 结合 VM + 容器接口，但启动仍需秒级
- **containerd**：偏轻量性 — 纯容器，性能最好，但隔离最弱
- **Knative**：偏弹性 — 基于 K8s 的 Serverless 框架，冷启动优化

**我们的教学项目**：不会在不可能三角上做极端选择，而是**理解每种选择的代价**，然后实现一个能展示核心机制的简化版本。

## 二、核心架构分层

一个完整的 Cloud Runtime 可以分为 **控制面（Control Plane）** 和 **数据面（Data Plane）** 两大平面：

```
┌─────────────────────────────────────────────────────┐
│                  Control Plane                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────┐  │
│  │ API Server│  │ Scheduler│  │ Controller Manager│  │
│  │ (声明式API)│  │ (调度决策)│  │ ( reconcile 循环) │  │
│  └──────────┘  └──────────┘  └──────────────────┘  │
│                      │                               │
│              ┌───────────────┐                       │
│              │   State Store  │                       │
│              │  (etcd/内存)   │                       │
│              └───────────────┘                       │
├─────────────────────────────────────────────────────┤
│                  Data Plane                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────┐│
│  │ Runtime  │  │ Network  │  │ Storage  │  │ FaaS ││
│  │ (沙箱隔离)│  │ (网络栈) │  │ (文件系统)│  │(函数) ││
│  └──────────┘  └──────────┘  └──────────┘  └──────┘│
│                                                      │
│  ┌──────────────────────────────────────────────┐   │
│  │              Node Agent (kubelet 等价物)       │   │
│  │  负责在具体节点上执行控制面的指令              │   │
│  └──────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────┘
```

### 控制面 vs 数据面

这是整个 Cloud Runtime 最核心的架构决策。理解它就理解了 Kubernetes 的灵魂。

**控制面**：负责"决定应该发生什么"
- 接收用户的声明式配置（"我要 3 个实例"）
- 做调度决策（"这 3 个实例应该放在哪些节点上"）
- 持续观察实际状态，驱动实际状态向期望状态收敛

**数据面**：负责"实际让它发生"
- 在具体节点上创建/销毁沙箱
- 配置网络规则
- 挂载存储卷
- 执行函数代码

**为什么这样分离？**

这是**关注点分离（Separation of Concerns）** 原则的系统级体现：

1. **可扩展性**：控制面可以管理成千上万个节点，因为它不需要关心具体怎么创建容器
2. **容错性**：数据面某个节点挂了，控制面可以发现并重新调度
3. **一致性**：所有节点看到同一个"期望状态"，避免配置漂移
4. **可替换性**：数据面的 runtime 可以从 runc 换成 Firecracker，控制面不需要改

## 三、六大核心模块速览

### 模块 1：隔离与沙箱（Isolation & Sandbox）

**核心问题**：如何在同一台机器上安全地运行多个互不信任的程序？

**关键概念**：
- Linux Namespace：PID/Network/Mount/UTS/IPC/User 六种隔离
- Cgroups：CPU/Memory/IO 资源限制
- Seccomp：系统调用过滤
- Capabilities：细粒度权限控制

**我们的实现**：用 Go 调用 `syscall` 包，创建 namespace 隔离的进程沙箱

**工业对标**：Firecracker（Rust microVM）、gVisor（Go 用户态内核）、runc（Go 容器运行时）

### 模块 2：调度与编排（Scheduling & Orchestration）

**核心问题**：给定一组任务和一组节点，如何决定每个任务在哪运行？

**关键概念**：
- 调度算法：bin-packing（紧凑放置）、spread（分散放置）、亲和性/反亲和性
- 资源模型：CPU/Memory/GPU 的请求（request）与限制（limit）
- 优先级与抢占
- 队列与公平调度

**我们的实现**：事件驱动的调度器，支持多种调度策略，用 Go channel 实现事件循环

**工业对标**：Kubernetes Scheduler、Nomad、Mesos

### 模块 3：网络抽象（Networking）

**核心问题**：隔离环境中的进程如何与外界通信？

**关键概念**：
- 虚拟网络设备：veth pair、bridge、vxlan
- IPAM：IP 地址分配与管理
- 网络策略：哪些容器可以和哪些容器通信
- Service Discovery：如何找到目标服务

**我们的实现**：基于 veth pair + bridge 的虚拟网络，支持跨节点 overlay 通信

**工业对标**：CNI、Flannel、Calico、Cilium

### 模块 4：存储抽象（Storage）

**核心问题**：容器的文件系统是临时的，如何持久化数据？

**关键概念**：
- 分层文件系统：overlayfs、AUFS
- Volume 生命周期：创建、挂载、卸载、删除
- 存储类与动态供应
- 快照与备份

**我们的实现**：基于 overlayfs 的分层文件系统 + volume 管理

**工业对标**：containerd snapshotter、CSI、Longhorn

### 模块 5：函数运行时（FaaS Runtime）

**核心问题**：如何实现毫秒级的函数冷启动？

**关键概念**：
- 事件驱动模型：HTTP、定时器、消息队列触发
- 冷启动优化：预热池（warm pool）、快照恢复、微 VM
- 函数生命周期：初始化 → 调用 → 冻结 → 恢复 → 销毁
- 并发控制：单实例并发 vs 多实例水平扩展

**我们的实现**：事件驱动的 FaaS 引擎，支持预热池优化

**工业对标**：OpenFaaS、Knative、AWS Lambda（Firecracker）

### 模块 6：控制面与 API（Control Plane & API）

**核心问题**：如何用一套统一的接口管理以上所有模块？

**关键概念**：
- 声明式 API：用户声明期望状态，系统驱动收敛
- 控制器循环（Reconcile Loop）：观察 → 比较 → 行动
- 最终一致性：不要求立即一致，只要最终收敛
- Watch 机制：客户端监听状态变化，而非轮询

**我们的实现**：声明式 API server + 控制器循环框架

**工业对标**：Kubernetes API Server、etcd、Controller Manager

## 四、核心设计哲学

理解以下五条设计哲学，就理解了 Cloud Runtime（以及 Kubernetes）的思想内核：

### 1. 声明式优于命令式（Declarative over Imperative）

**命令式**："创建一个容器，然后给它分配 IP，然后挂载存储"
**声明式**："我期望存在一个容器，它有这些资源需求，这个网络配置，这个存储卷"

区别在于：命令式告诉系统**怎么做**，声明式告诉系统**要什么**。

为什么声明式更好？
- **幂等性**：同样的声明执行多次，结果一样
- **自愈**：系统持续检查实际状态是否匹配期望状态，不匹配就修复
- **可审计**：所有期望状态都有版本记录，可以回滚
- **可组合**：多个声明可以组合，不会互相冲突

### 2. 控制面与数据面分离（Control/Data Plane Separation）

控制面做决策，数据面做执行。分离后：
- 控制面可以集中管理海量节点
- 数据面可以独立演进（换 runtime 不需要改控制面）
- 故障域隔离（数据面挂了不影响控制面做决策）

### 3. 最终一致性（Eventual Consistency）

Cloud Runtime 不追求强一致性。为什么？
- 分布式系统中强一致性 = 低可用性（CAP 定理）
- 最终一致性允许系统在短暂不一致的情况下继续运作
- 控制器循环会持续驱动系统向期望状态收敛

**Reconcile Loop 是实现最终一致性的核心机制**：
```
for {
    desired := getDesiredState()    // 从 API server 读期望状态
    actual := getActualState()      // 从节点读实际状态
    if desired != actual {
        actions := computeActions(desired, actual)
        execute(actions)            // 驱动实际状态向期望状态收敛
    }
    sleep(shortInterval)
}
```

### 4. 一切皆资源（Everything is a Resource）

在 Cloud Runtime 中，容器、网络、存储、函数都是"资源"。每个资源有：
- **Spec**：用户声明的期望状态
- **Status**：系统观察到的实际状态
- **Metadata**：名称、标签、注释、版本

这种统一模型的好处：
- 所有资源用同一套 API 操作（CRUD + Watch）
- 资源之间可以互相引用（标签选择器）
- 扩展时只需要定义新资源类型（CRD）

### 5. 小而可组合（Small and Composable）

Unix 哲学在 Cloud Runtime 中的体现：
- 每个组件做好一件事
- 组件之间通过明确的接口通信
- 不做 monolith，做可插拔的组件集合

Kubernetes 的 CRI（Container Runtime Interface）、CNI（Container Network Interface）、CSI（Container Storage Interface）就是这一哲学的产物：
- 想换容器运行时？实现 CRI 接口
- 想换网络方案？实现 CNI 接口
- 想换存储方案？实现 CSI 接口

## 五、我们的教学项目定位

### 我们要做什么

构建一个 **Mini Cloud Runtime**，用 Go 从零实现以上六大模块的核心机制。目标不是生产可用，而是**让每个核心概念都有可运行的代码来验证理解**。

### 我们不做什么

- 不做生产级的高可用（不需要多副本控制面）
- 不做生产级的安全（不需要完整的 RBAC）
- 不做生产级的性能优化（不需要 CRI/CNI/CSI 的完整实现）
- 不做 Windows/macOS 兼容（依赖 Linux 内核特性）

### 学习路径

```
模块 0 → 模块 1 → 模块 2 → 模块 3 → 模块 4 → 模块 5 → 模块 6
概览     隔离沙箱  调度编排   网络抽象   存储抽象   FaaS引擎  控制面API
 │         │         │         │         │         │         │
 │         │         │         │         │         │         │
 建立全局   从底层    在隔离    给沙箱    给沙箱    在运行时   把一切
 认知框架   开始构建   之上做    配网络    配存储    之上做    串起来
                    决策               函数执行   统一管理
```

每个模块的产出：
1. **设计文档**：为什么 + 怎么做 + 工业对比
2. **可运行代码**：Go 实现的核心机制
3. **测试**：验证理解是否正确
4. **可视化**（可选）：React 面板观察行为
